# 主功能案写作规范

本文件定义主功能案的写作规范：起草过程的思考顺序、功能规则与界面规则的分工、以及高频常见错误。内容边界（什么写、什么不写）见 `feature-spec-boundaries.md`。

## 起草顺序

下面是**起草过程中的思考与落笔先后**，不是成稿的章节排版顺序——成稿章节顺系统自身逻辑组织，不套僵化模板（见 SKILL.md §文档粒度 与 §文档章节模型）。

1. 先明确目标和边界。
2. 再写核心流程。
3. 再写系统规则。
4. 再写界面状态与交互。
5. 最后补配置、数据、资源需求。

除非任务本身只是轻量 UI 说明，不要从 UI 控件堆描述开始写。

目标和边界是起草输入，不是成稿章节。完成范围审查后，按 `feature-spec-boundaries.md` 的“范围信息落点”生成成稿：简介只含设计目的与功能简述，关键决策只列实际采用的实现决策，详细规则只写当前有效业务规则。目标玩家、目标用户或目标行为不另成决策行，排除项名称不在其他章节继续传播。

## 功能规则与界面规则

功能规则写系统如何运转：

- 解锁、开启、关闭、刷新、重置。
- 玩家权限、条件、限制。
- 状态变更和持久化。
- 结算、奖励、消耗、回流。
- 跨系统依赖和边界。

界面规则写功能如何表现：

- 页面入口、默认状态、显隐、排序。
- 按钮、页签、列表、弹窗、红点、角标。
- 点击反馈、禁用态、空态、满态、错误态。
- 文案展示、多语言 key、数字展示规则。

同一结论同时影响功能和界面时，功能规则写系统结论，界面规则写控件表现。

判断边界时看“系统是否因此改变玩家能做什么”，不要只看句子里是否出现按钮、页签或 LOD：

- 自动打开、允许/禁止进入流程、强制跳转、确认/取消结果属于功能规则，主案必须保留。
- 控件位置、尺寸、样式、动效、截图编号和多语言 key 属于界面规则，可进入界面标注。
- 同一句同时含玩家行为与视觉参数时，先拆成两条再分别归属，禁止整句迁移。

文档归属正确不等于可以立即从主案移出。准备把控件参数、多语言 key、配置字段、技术证据或测试项迁往派生文档时，必须先确认目标文件已经存在，并核验具体内容已经落入对应章节。目标不存在或内容未命中时，原内容暂时保留在主案；精简报告标为 `protect`，注明“暂时保留；建议移动到派生文档：<文件名或文档类型>。”只有迁移闭环后才能从主案删除并计入精简成果。

## 成稿清理说明

正式主案只保留仍参与评审的规则，不把写作过程和已经落实的纠错单独列成规则：

- 成稿按下表分层，详细规则只陈述当前最终状态：

| 信息类型 | 唯一落点 | 成稿写法 |
|---|---|---|
| 当前最终规则 | 详细规则 | 直接写当前触发、条件、行为和结果，不复述“原来怎样” |
| 多版本变更过程 | 变更记录 | 只在对应版本写一次“从 A 调整为 B” |
| 仍需处理的旧数据/老客户端 | 兼容与边界 | 写清旧状态的识别条件、迁移/降级动作和最终结果 |
| 未完成的写作或资源清理 | 界面标注或交付 Checklist | 跟踪占位符、换图、补资源等执行事项 |

- “当前版本”“本版本”“现已改为”“原规则废止”等时间依赖措辞不进入详细规则，改写为不依赖阅读时间的当前状态。“本期”只用于起草阶段的范围审查，不作为成稿章节或稳定业务规则的包装词。
- 仍影响计算的语义并入对应参数、公式或机制定义。例如“百分比成长按百分点解释”写在该参数用途内，不另起一条写作说明。
- `X%`、占位文案替换、截图换图等未完成事项进入界面标注或交付 Checklist；最终主案正文不保留“正式界面记得替换”一类提醒。
- 示例、术语或机制名称已经改正后，以正确正文作为 SSOT；“旧示例不是 A、现已改为 B”不再留在详细规则。确需追溯实际版本变更时，只在变更记录保留一次。

## 多级无序列表与长规则

规则正文采用“一级规则主题 + 二级条件、分支与反馈”的结构：

- 一级 bullet 说明这组规则处理什么，必要时用加粗短语命名。
- 二级 bullet 分别承载触发条件、成功结果、失败结果、不满足提示与例外。
- 同一规则出现成功/失败、满足/不满足、确认/取消等两个以上分支时，直接拆成二级 bullet；不要把多个结果压在同一行。
- 三种以上状态需要按相同维度比较时使用表格，不把表格重新展开成平铺列表。
- 只有单一结论、没有分支或独立反馈的规则才保持一行。

推荐写法：

```markdown
- **确认保存**
  - 确认时服务器重新校验功能解锁、机制开放、来源和英雄条件。
  - 校验成功：保存当前编队并刷新状态。
  - 校验失败：保留原选择，弹窗继续展示并刷新失败原因。
```

## 常见错误

- 把界面控件描述当成功能规则。
- 在多个章节重复描述同一规则，后续修改时产生冲突。
- 为了完整而保留大量空章节。
- 把待确认问题写进正式功能案正文。
- 替程序定义组件 ID 或服务端字段。
- 把数值策划负责的平衡数值当成功能案缺漏。
- 只写正常流程，不写边界、异常、空态、满态、禁用态。
- 只写页面展示，不写系统如何更新状态。
- 把主动作、成功分支、失败分支和提示用分号压在同一条 bullet 中。
- 把占位符清理、换图提醒或已经完成的示例纠错当成独立功能规则。
- 在详细规则重复“原来 A、现改为 B”，或用“当前版本”“本期”包装本应长期成立的规则。
- 把起草时的目标、范围、对标和排除项原样输出为独立章节，或换名为目标用户、竞争边界、不创建项等决策行与派生说明继续保留。
