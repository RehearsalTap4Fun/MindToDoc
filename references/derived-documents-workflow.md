# 派生文档类型与生成流程

本文件是项目交付模式、派生文档类型、触发条件和生成顺序的唯一规则来源。生成或重整前先判定采用“小型需求单文档”还是“完整功能案”模式；仅审查、同步或局部修改不自动扩大为整套补生成，局部修改须检查已有派生中受影响的内容。

## 交付模式判定

### 小型需求单文档

需求满足以下任一前提时，可进入小型需求判定：用户明确要求小型需求或单文档交付；需求属于既有功能内的单一流程优化。同时，全部变更必须能够在一份文档内清楚说明。典型内容包括少量规则调整、文案、一个简单常量、简单弹窗或列表提示。

采用该模式时：

- 只交付 `output/<功能名>.md`；常量语义与初始值、精确文案、简单界面规则和已确认效果图直接写入主案。
- 简单界面效果图可存放在 `output/ui-design/<功能标识>/` 并嵌入主案。主案已能明确对应界面与规则时，不制作红圈标注图或独立 `-界面标注.md`。
- 不生成 BI、美术、音效、配置结构四类固定派生，也不生成 Checklist 或测试用例；用户明确要求某项，或内容已经复杂到需要独立评审时，再按对应入口单独生成。
- 仍须完整写清主体、触发、条件、动作、分支、反馈和异常；单文档是交付收拢，不是规则删减。

出现以下任一情况时采用完整功能案模式：新增完整系统或活动、涉及多个相互独立的模块、需要独立 BI 分析方案、新增美术或音频资产、复杂配置表结构、复杂多界面交互或需要逐控件标注。用户明确要求完整交付包时也采用完整功能案模式。若用户指定交付形式，在不丢失必要业务规则的前提下优先遵从。

### 完整功能案

完整功能案执行下列固定与条件派生流程。四类固定文档不得因精简、完全复用或未提供成品素材而跳过。

## 类型与入口

| 类型 | 生成规则 | 内容来源与生成入口 | 产物 |
|---|---|---|---|
| BI 日志需求 | 固定生成 | `vendor/skills/bi-log-requirements/`（vendor 自本机 `bi-log-requirements` skill）：从主案提取分析目标与行为，核对现有打点及公共日志，再写字段级需求；四列表结构固定为「日志触发逻辑｜日志表名/类型｜字段名｜字段含义/取值」，一张连续表不按模块拆分 | 钉钉表格（axls），结构对齐《K1_BI日志统计需求》样例库（node `dpYLaezmVNLROXARIZwOlNLK8rMqPxX6`），挂主案子节点；本地保留同内容 `output/<功能名>-BI日志需求.xlsx`（权威，用该 skill 的 `scripts/gen_bi_requirements_excel.py` 生成）与 `.md`（可编辑源，供人工改字段用） |
| 美术需求 | 固定生成 | `art-requirements-reference.md` + `../templates/derived-art-requirements.md`：提取独立视觉资产 | `output/<功能名>-美术需求.md` |
| 音效需求 | 固定生成 | `vendor/skills/audio-production-pipeline/` 的 K1 独立需求模式（`references/k1-demand-only.md`）；先查音效库，按该模式生成与校验 | `output/<功能名>-音效需求/audio_demand.xlsx`，不进入生产包流程 |
| 配置结构 | 固定生成 | `../templates/derived-config-tables.md`；核对现有配置并描述新增、修改及复用结构 | `output/<功能名>-配置表结构.md` |
| 界面标注 | 用户提供界面效果图后生成 | `ui-annotation-reference.md`；先看图、标注并经用户审核，再写图文及本地化表 | `output/<功能名>-界面标注.md` + 标注素材 |
| 开发 Checklist | 用户确认生成后执行；已明确要求视为确认 | `vendor/skills/dev-checklist-generator/`，读取主案及已完成派生，沿用已确认拆解粒度 | Excel，遵循专用 Skill |
| 测试用例 | 用户确认生成后执行；已明确要求视为确认 | `vendor/skills/slg-testcase-generator/` 的完整模式；只有明确要求快速静态预检才限时限量 | 本地 Markdown／Excel 或已授权的在线表格，格式不改变覆盖范围 |

> **vendor 说明**：以上四个专用 Skill 已整体拷贝至 `vendor/skills/<skill-name>/`，随本仓库分发，clone 后即可直接使用，不依赖本机全局 skill 安装。`slg-testcase-generator` 的真实凭据文件（`config.json`/`token.json`）未随仓库分发，仅保留 `.example`/`.template`，新设备需自行创建并填入真实值后才能跑通 Google Sheets 相关功能；不影响本地 Markdown/Excel 交付路径。上游 skill 更新时需人工比对差异后决定是否同步覆盖 vendor 副本，避免规则漂移。

技术交接、程序结构和 AI 视图不属于本项目派生交付。业务状态、流程、异常与兼容仍在主案定义。测试配置是额外的数据产物，只有用户要求时走 `test-config-generator`；K1 正式配置的查询或修改走 `config-table-editor`，不因生成配置结构文档自动修改正式表。

完整功能案先核查主案和现有来源：没有新增项时，在对应文档保留简短的核查结论与可定位的复用依据，不虚构资产、日志或配置字段，也不制造空白需求行。缺少影响正确性的业务决策或必要输入时，继续澄清，说明该文档尚未完成；“未查到”不等于“没有需求”。无现成音频不妨碍拆音效需求。已有同用途且版本一致的文档可作为该类交付，不重复另建。

专用 Skill 在使用前发现并读取；不可用时说明缺失及受影响的产物，不以自编格式冒充已按该 Skill 完成。这里只承接需求生成；音频生产、资源导入、配置落地和发布按各自任务授权执行。

自由格式的派生文档（美术需求、BI 日志需求的本地 `.md`、音效需求钉钉端的只读镜像）只写两部分：**需求正文本身**（资产清单/复用清单、四列日志表等）和**待确认项**。不写整理日期、来源文档、规则依据、生成方式等元信息段落，不写"结论先行"式的过程叙述，不写"交付格式建议"或"关联文档"链接列表——判断过程是起草动作不是交付内容，关联文档已经在主案「派生文档说明」里有了；命名建议、切图规格这类零碎信息并入表格备注列，暂时无法确定的信息折进待确认项，不单独开章节铺陈"核对了什么/没核对什么"。

派生文档的目标格式若为 axls（钉钉表格）而当前环境没有 spreadsheet 读写 MCP（`get_all_sheets`/`get_range`/`update_spreadsheet_range` 一类）时，不代表做不了——改用「本地生成 xlsx + 导入」路径落地为真正的钉钉表格，具体步骤见 `dingtalk-sync-reference.md`「导入本地表格生成钉钉表格」一节；不要因为读不到就退回到 adoc 里贴一张 markdown 表格充数。

## 宣讲 / 演示（按需，非固定派生）

主案与固定派生齐备后，如需向其他职能做方案宣讲，可额外生成一份单文件 HTML 宣讲网页；这不是七类固定/条件派生之一，不影响成稿门禁判定，仅在用户明确要求"宣讲""讲解方案""PPT""网页演示"等场景触发。

| 用途 | 生成入口 | 产物 |
|---|---|---|
| PPT 骨架、翻页交互、演讲者模式、两套视觉体系（杂志风/瑞士风） | `vendor/skills/guizang-ppt-skill/`（vendor 自 https://github.com/op7418/guizang-ppt-skill ，AGPL-3.0） | `output/<功能名>-宣讲.html`（单文件，浏览器直接打开） |
| 页面内流程图、对比图、时间轴等图表元素的设计规范 | `vendor/skills/diagram-design/`（vendor 自 https://github.com/cathrynlavery/diagram-design ，MIT） | 内嵌于宣讲网页或独立图表 HTML |

- 内容来源须是已完成的主案与派生文档，不新增未经确认的规则或数据；图表和界面标注截图直接引用 `output/` 下已有产物，不重新生成事实。
- 两个 Skill 均已 vendor 到本项目、随仓库分发；`guizang-ppt-skill` 的上游自动更新检查（`git fetch`）在 vendor 版本中已跳过，人工比对差异后决定是否同步。
- 许可证：`guizang-ppt-skill` 为 AGPL-3.0，仅限本项目私有内部使用（不对外分发、不作为网络服务提供第三方访问），不触发开源回馈义务；对外分发或部署为可远程访问的服务前需重新评估合规性。`diagram-design` 为 MIT，无使用限制。

## 完整功能案生成顺序

1. **整理主案**：先确认相关业务规则，确定唯一详细落点，完成主案初步精简。
2. **确定交付**：纳入四类固定文档；检查是否已有界面效果图；Checklist 和测试用例尚未确认时逐项询问，等待期间继续固定文档。缺图只阻塞界面标注，不阻塞其他交付。
3. **准备来源**：核对现有文档、配置、资产与日志；只询问环境无法查明的必要输入，沿用已有确认。
4. **生成或更新**：按类型入口执行。配置字段未落表时明确为设计结构；已有实际 Excel 时核验后引用其结构；本次另有测试配置任务时，在表生成后回写配置结构说明，避免两份字段定义独立漂移。冲突先解决，不自动以测试表覆盖正式配置或业务规则。
5. **联合检查**：对主案及本次所有派生执行精简门禁；检查四类固定交付、条件生成的依据、规则对应、真实来源、文件与链接、版本及专用 Skill 当前阶段的校验。字段、资源与日志定义各有唯一落点，派生文档引用业务规则，不重新定义。BI 对照实际触发与字段语义判定是否复用；独立音效需求不套生产包校验；测试用例按已确认规则覆盖判定，不用最低条数替代覆盖。已授权范围内发现遗漏当轮补齐，缺必要输入则报告部分完成。
6. **交付与同步**：只链接真实完成且内容匹配的文件。缺必要输入的固定文档须报告未完成，不能宣称整套完成。后补界面标注或其他派生后，重新检查受影响内容再按授权同步；Markdown、Excel 和图片按对应媒介处理，不能一律套 Markdown 转换器。

主案规则变化时检查四类固定文档及已生成的条件文档，更新受影响项；不能更新的明确标记待更新，不能继续作为当前版本交付。不因变更自动新增未经确认的 Checklist 或测试用例。
