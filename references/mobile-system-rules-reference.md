# 手游系统按需规则参考

本文件承载 `SKILL.md` 中不适合展开的手游系统专项检查：逐系统交付物判定、红点规则、线上数据兼容和配置表边界。使用时先判断是否适用，不要为了完整而硬凑章节。

## 逐系统交付物判定

规则说明是必写项，其余交付物按系统复杂度判定：

| 交付物 | 通常需要 | 通常可跳过 |
|---|---|---|
| 流程图 | 多状态流转、分支决策、时序或依赖复杂 | 单条开关规则、纯展示文案、逻辑一两句能说清 |
| 界面标注 | 有专属 UI、多屏交互、布局需对齐 | 纯后台逻辑、无界面、只复用通用弹窗 |
| 配置表派生 | 需独立配表、活动投放、奖励/消耗/次数由配置控制 | 完全复用既有配置、无数值与投放规则 |
| 红点规则 | 有入口、奖励可领取、次数重置、新内容解锁、活动阶段变化或待办状态 | 纯后台模块、无玩家可感知入口 |
| 线上数据兼容 | 线上项目、活动/赛季玩法、跨服/联盟/排行/热更相关系统 | 未上线验证项目、未上线新项目、无历史数据影响 |

判定后只写已采用的交付物；跳过的交付物不写空章节。若用户明确要求产出实现清单、接口、字段 schema、QA 或界面标注，将其作为派生文档，不塞进主功能案。

## 配置表边界

主功能案内只写配置表名称、用途、影响哪些规则，以及未定数值“由配置表定义”。不要在主功能案里编字段、类型、默认值或最终数值。

需要字段 schema、状态机、实体结构、跨系统契约时，派生 AI 视图或技术交接文档；这些派生内容必须回贴规则依据，不能替代主功能案。

### K1 关键常量关联

K1 项目把关键常量 ID 作为策划评审、配表核对和问题追溯的锚点。对直接驱动业务分支的阈值、上限、时长、概率等配置，主功能案应保留“语义名称 + 由常量配置决定 + 已知常量 ID”，精简时标记为 `protect`，不得因为它是 ID 就机械迁出。

- 已知常量 ID：在对应业务规则旁标注，例如：
  - **占领名额配置**
    - 占领上限由常量 `10135678` 配置。
    - 低余量阈值由常量 `10135681` 配置。
- 未提供常量 ID：只写“由常量配置决定”，不得猜测 ID；落表前由配置负责人补录关联。
- 主案仍不展开字段 schema、字段类型、默认值或最终调优数值；这些内容进入配置表结构派生文档。
- 仅用于实现排查、任务替换或批量落地的普通配置 ID 清单不属于业务规则，仍迁移到开发 Checklist 或配置清单。

### PRD/需求文档 → 测试配置的 ID 规则

PRD 与程序需求文档里的配置示例（`ID = 1, 2, 3, 4` 这类）只是表结构示意，**不是真实落地 ID**。把需求落到 `output/test-config/` 时:

- 实际 ID 沿用**配置表结构派生文档** `## 填表约定 → ### ID 段交叉引用` 表里给出的段位（如 `ReceiveDecision 5001-5004` / `PlayerStyle 5101-5104` / `FirstTouchAnim 5201+`）。
- 该派生文档没有声明段位的，新增表自己挑一个不与已有段冲突的整百起点（推荐 1000 的倍数留扩展空间），**同时回贴一行到 ID 段交叉引用表**，避免下次再判断。
- 引用列（如 `PlayerStyleCfgID`、`ReceiveDecisionCfgID`）也要按真实段写,不要拷 PRD 示例里的 1/2/3。

## 红点规则

红点分清系统规则和界面规则：

- 系统规则：触发条件、消除条件、刷新时机、状态持久化。
- 界面规则：展示位置、入口链路、层级、角标样式、优先级表现。

按需写清：

- 触发条件：什么状态变化导致亮红点，如可领、可买、次数已重置、新内容解锁、活动开启或即将结束。
- 展示位置：红点挂在哪条入口链路，如主界面图标、页签、子按钮、列表项。
- 消除条件：领取、查看、操作完成、过期、跨日刷新后何时熄灭。
- 刷新时机：与日切、活动阶段、次数重置、服务器推送或重新登录相关的重新计算规则。
- 优先级：多红点并存时的展示策略；若项目有统一红点规范则引用，未定时标明待谁拍板。

常见漏项：只写“有奖励显示红点”，但没写领奖失败后是否保留红点；只写按钮红点，没写上级入口是否冒泡；只写跨日刷新，没写活动结束或热更后如何重算。

## 线上数据兼容

线上数据兼容是边界情况处理的专项。线上项目先写文档级总则，各模块只写本模块特例；不要在“边界情况处理”和“数据兼容”里重复两套口径。

文档级总则常见覆盖：

- 客户端版本策略：老客户端连新服、字段缺失、协议差异、强更节点。
- 转服、跨服与合服：进度、次数、排行、邮件、未领奖励、补偿和 ID 归属。
- 联盟/社交归属：退盟、加盟、解散对个人和联盟维度数据的影响。
- 热更与活动窗口：配表变更、进行中状态、旧数据迁移、回滚或结算口径。

模块级写法：

- 有特例：引用总则后写清本模块例外。
- 无特例：写“遵循数据兼容总则，无额外约定”。
- 不适用：非线上项目可写“本项目不涉及线上数据兼容”。

逐模块重点核对：

- 老客户端 × 新服务器：缺字段或旧协议时默认行为、是否降级展示、是否拒绝参与。
- 活动中转服：进度、次数、未领奖励、排行、联盟贡献是否保留或折算。
- 退盟 / 加盟 / 解散：联盟绑定数据清零、冻结还是随玩家迁移。
- 热更 / 配表变更：进行中状态如何结算，旧档数据如何迁移或作废。
- 断线重连 / 重复请求：幂等与重复领取防护。
