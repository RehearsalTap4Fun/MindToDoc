# 主功能案写作规范

本文件定义主功能案的写作规范：起草过程的思考顺序、功能规则与界面规则的分工、以及高频常见错误。内容边界（什么写、什么不写）见 `feature-spec-boundaries.md`。

## 起草顺序

下面是**起草过程中的思考与落笔先后**，不是成稿的章节排版顺序——成稿章节顺系统自身逻辑组织，不套僵化模板（见 SKILL.md §文档粒度 与 §与 system-design-doc 章节对应）。

1. 先明确目标和边界。
2. 再写核心流程。
3. 再写系统规则。
4. 再写界面状态与交互。
5. 最后补配置、数据、资源需求。

除非任务本身只是轻量 UI 说明，不要从 UI 控件堆描述开始写。

## 功能规则与界面规则

功能规则写系统如何运转：

- 解锁、开启、关闭、刷新、重置。
- 玩家权限、条件、限制。
- 状态变更和持久化。
- 结算、奖励、消耗、回流。
- 跨系统依赖和边界。

界面规则写功能如何表现：

- 页面入口、默认状态、显隐、排序。
- 按钮、页签、列表、弹窗、红点、角标。
- 点击反馈、禁用态、空态、满态、错误态。
- 文案展示、多语言 key、数字展示规则。

同一结论同时影响功能和界面时，功能规则写系统结论，界面规则写控件表现。

## 常见错误

- 把界面控件描述当成功能规则。
- 在多个章节重复描述同一规则，后续修改时产生冲突。
- 为了完整而保留大量空章节。
- 把待确认问题写进正式功能案正文。
- 替程序定义组件 ID 或服务端字段。
- 把数值策划负责的平衡数值当成功能案缺漏。
- 只写正常流程，不写边界、异常、空态、满态、禁用态。
- 只写页面展示，不写系统如何更新状态。
