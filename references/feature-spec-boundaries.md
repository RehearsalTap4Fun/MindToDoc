# 主功能案边界

本文件定义主功能案的内容边界：什么内容写进主功能案、什么内容不写、数值与奖励写到什么粒度。写作规范（起草顺序、功能/界面规则分工、常见错误）见 `feature-spec-writing.md`。

## 文档定位

- 功能案回答：要做什么功能、为什么做、玩家如何使用、系统如何判定、结果如何反馈。
- 功能案不是技术方案、接口文档、QA 测试用例、埋点表、资源表或数值配置表。
- 内部讨论、草稿路径、源素材路径、临时备注、未决问题和协作过程不要写进主功能案正文。

## 范围信息落点

范围审查是起草前的内容过滤，不是成稿章节。主功能案不设置“目标与范围”“目标与对标”“目标与参考”“非目标”等独立章节，也不把同一批信息换名为相邻清单。

| 输入信息 | 成稿落点 |
|----------|----------|
| 目标玩家或目标行为 | 只有确实影响玩法价值时，才自然并入“简介 / 设计目的”；不单列标签，也不写成“目标玩家 / 目标用户 / 目标行为”关键决策行 |
| 功能开放门槛 | “关键决策”摘要，并在对应详细规则写完整判定与反馈 |
| 跨系统边界、业务限制 | “关键决策”摘要或对应详细规则；用当前正向约束表达 |
| 参考玩法 | 只有实际改变设计选择时，才写入相关关键决策或规则；“无参考”不进入成稿 |
| 排除项、非目标 | 先提炼实际采用的正向业务规则；排除项名称不进入主案。用户明确要求追踪后续工作时，写入交付 Checklist |

功能简述和详细规则已经覆盖的模块，不再通过“本期范围”重复枚举。纯粹说明“不做什么”的内容在范围审查后即停止传播，不进入变更记录、关键决策、详细规则、界面清单或派生文档说明；若它隐含必要的开发判定，只保留对应正向规则，不点名被排除的功能。例如“个人进度按玩家记录”已经定义数据维度，无需再补“不做联盟排行榜”。

## 主功能案不默认包含的内容

除非用户或项目明确要求，不要把下列内容放入主功能案：

- 客户端/服务器职责划分。
- 接口字段、协议、数据库结构。
- 研发任务拆解和工时。
- QA 验收检查点或测试用例。
- 埋点技术方案。
- 具体资源 ID、组件 ID、程序类名。
- 浏览器原型、playtest、HUD 原型说明。
- 过细的数值平衡公式和最终数值。
- 目标与范围、目标与对标、非目标等独立清单。
- 无参考玩法、无新增内容、明确不做某项功能等排除式占位说明。

这些内容需要时应做成派生文档。

## 数值与奖励边界

- 功能案应说明哪里有奖励、奖励如何触发、领取条件、消耗产出机制和异常情况。
- 功能案不默认要求给出最终奖励内容、经济投放量、成长曲线或平衡参数。
- 公式只在说明功能逻辑必须时使用，例如取历史最高、阈值判定、次数累计、权重选择。
- 纯条件判断和状态分流优先用自然语言或表格，不要强行包装成公式。
