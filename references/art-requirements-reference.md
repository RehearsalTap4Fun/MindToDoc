# 美术需求提取与落地参考（mindtodoc 随附）

把主策划案与界面标注里**真正需要新增或变更的视觉资产**整理成美术可执行的需求表（self-contained）。本文件只讲"提取什么、怎么判断、表格怎么写"；钉钉落地流程见 `dingtalk-sync-reference.md`。

## 定位与边界

- **固定生成**：完整功能案四类固定派生之一，见 `derived-documents-workflow.md`。完整功能案没有新增视觉资产时仍要生成本文档，正文写清复用依据，不能跳过；小型需求单文档模式不适用本条。
- **不是什么**：不是玩法规则文档（规则在主案），不是界面控件级标注（控件、状态、key 在 `-界面标注.md`，需要用户供图后才产出）。本文档只回答"美术要画/做什么、优先级多高、能不能复用已有资源"。
- **来源**：主案的「界面设计」「详细规则」与已完成的 `-界面标注.md`；没有界面标注时，只能从主案的界面需求清单和规则描述推断，不能杜撰截图里才能确认的细节。
- **产出内容**：只有「新增资产清单」「复用清单」「待确认项」三部分，不写整理日期/来源文档等元信息段落，不写交付格式建议、不写关联文档链接——这些交给主案的「派生文档说明」承接。

## 复用优先，不因新功能就臆造整套新美术

多数 K1 功能是在现有系统（活动框架、联盟、迁服、商店、通行证等）上叠加规则变化，界面大量复用现有控件、数字格式、弹窗框架。**默认假设是复用**，只有以下情况才判定为新增视觉资产：

1. 现有界面里**不存在**语义相近的控件（如全新的状态标签、全新的强调色语义）。
2. 玩法引入了**新的实体**需要专属呈现（新角色、新道具外观、新场景、新关卡表现），且不能靠改文案/换色复用已有资源。
3. 主案明确要求某处需要**独立的情绪/氛围表达**（如本例冷库预告弹窗需要传达"即将关闭"的紧迫感，而非常规庆典风格弹窗能覆盖）。

写文档前先过一遍界面标注和主案的规则描述，明确列出"这些控件/流程复用了什么现有系统"，再收敛出真正的增量。这是起草阶段的判断动作，不必单独写成文档里的"结论先行"段落——判断结果直接体现为「新增资产清单」和「复用清单」两张表的取舍。

## 判断准则

| 情况 | 判定 | 说明 |
|------|------|------|
| 已有界面标注里明确写"沿用原控件"/"复用既有格式" | 复用，不列入新增清单 | 可在「复用清单」小节列出，作为核查记录，不占用新增资产篇幅 |
| 新增了文案/数值展示，但控件形态与现有列表/卡片一致 | 复用 | 换皮不算新增 |
| 新增了一个此前不存在语义的标签/角标/强调色 | 新增，通常 P0 | 因为高频出现在多个复用界面上，属于影响面最广的一类增量 |
| 新增了一屏此前没有对应模板、且需要独立情绪表达的弹窗/场景 | 新增 | 按「资产分类」拆解需要的具体元素 |
| 主案要求的行为在现有系统里有但**表现方式明确要求不同**（如强调"紧迫感"区别于日常庆典） | 新增 | 不能因为"有类似弹窗"就直接判定复用，需说明为什么现有资源不满足 |
| 界面标注/主案未覆盖到的屏（如仍待收图） | 不写控件级内容，只在「待确认项」标注待收图后复核 | 不得凭空假设未出现的界面需要什么资产 |

## 资产分类维度（按需选用，不强制套满）

不要求每份需求文档都填满以下类别；只列这次功能实际涉及的：

- **角色/生物**：立绘、模型、头像、动作
- **场景/背景**：主界面背景、局内场景、氛围插画
- **UI 页面**：新增或大改的整屏 UI 皮肤
- **图标/道具**：局内外道具、货币、资源图标
- **标签/角标/强调色**：状态标记、稀有度、推荐/警示类视觉标记
- **动效/反馈**：入场动画、成功/失败反馈、过场转场

## 优先级判定

- **P0**：阻塞核心链路（不做玩家无法完成主流程），或出现在多个复用界面、影响面广的通用元素（如本例的推荐标签）。
- **P1**：影响体验完整度但不阻塞主流程（氛围插画、次要页面皮肤）。
- **P2**：可延后、不影响首批交付（宣传物料、进阶动效、稀有度细分皮肤）。

## 资产清单表格规范

固定列：

| 项目/资产 | 用途 | 优先级 | 备注 |
|-----------|------|--------|------|

- **用途**列须能定位到主案或界面标注的具体规则位置，不写空泛描述。
- **备注**列写设计约束（如"需要与骚扰感和紧迫感之间取得平衡"）、依赖关系或与复用资产的差异点；命名建议、切图规格等交付格式类信息也放这里按需一两句带过，不单开章节。
- 数量已知且成组（如多个角色立绘）时可加"数量"列；单项资产不必强行套数量列。

## 复用清单表格规范

用于记录"已核查为复用、不产生新美术需求"的控件，作为审计依据，不是可选章节：

| 控件/资产 | 复用依据 |
|-----------|----------|

复用依据须指向具体来源（界面标注原文措辞、主案规则原文、或已知的现有系统名称），不能只写"复用现有"四个字。

## 待确认项写法

只写**真正需要美术/UI/策划共同拍板**的开放问题，不用它掩盖"没想清楚"：

- 是新画还是改现有模板文案，这类"工作量取舍"问题可以待确认。
- 玩法规则本身未定（如具体数值、具体分级）不属于本文档待确认范围，应退回主案先澄清。
- 尚未收到截图的界面，在此注明"暂按复用处理，收图后复核"，不单独开章节说明覆盖范围。

## 自检清单

- [ ] 已对照界面标注（或主案界面需求清单）逐条判断复用/新增，不是凭空列资产。
- [ ] 复用清单里每条都有可定位依据，不是空泛的"复用现有"。
- [ ] 优先级判定有理由，不是全员 P0 或全员 P1。
- [ ] 待确认项都是真正需要他人拍板的问题，不是策划自己没想清楚的规则漏洞。
- [ ] 没有臆造截图里才能确认的控件级细节（无图/无标注时不写）。
- [ ] 文档只有「新增资产清单」「复用清单」「待确认项」，没有整理日期/来源文档/交付格式建议/关联文档等外围段落。
