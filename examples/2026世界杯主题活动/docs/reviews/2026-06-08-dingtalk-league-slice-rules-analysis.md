## 结论

这版钉钉文档相比仓库里的早期评审稿已经收敛了几个关键问题：
- 正式关卡操作模式锁定规则已经明确。
- 切片配置已经拆成 `slice_type_def / slice_preset / slice_instance` 三层。
- 积分赛、排名、淘汰赛的主要数据口径比之前更完整。

它已经可以支持测试关卡配置和程序侧原型联调，但还没有完全达到“无需额外产品约束即可批量出关”的状态。当前最值得优先收口的是“积分口径公平性”和“切片成功、进球、奖励三者映射关系”。

## 已经合理的部分

### 1. 正式关卡首个非守门切片锁整关模式

这是合理的，原因有三点：
- 直接降低客户端状态复杂度，避免每切片切模式导致教学、按钮态、回溯态全部分叉。
- 能形成稳定的操作偏好分流，便于后续分析划线和弹弓哪套更适合留存和付费。
- 守门切片单独强制划线，也避免“整关锁了弹弓后守门无法处理”的规则冲突。

### 2. 三层切片配置结构是对的

`type_def -> preset -> instance` 的拆法合理，尤其适合这个题材：
- `type_def` 固定引擎能力边界。
- `preset` 承担可复用摆位资产。
- `instance` 承担关卡内具体玩法和局部覆盖。

这比直接在 `level_config` 里堆一串匿名切片参数更稳定，后续美术摆位预览、数值调参、AB 测试都更容易做。

### 3. 仅守门切片有反应时间，其他切片纯暂停

这对移动端竖屏是合理的：
- 降低非守门切片的实时压力，突出“思考后出手”的休闲定位。
- 守门切片天然适合做短时反应压迫，用来拉开玩法节奏。
- 对教学和数值调试也更简单，不需要给所有切片都做时间曲线。

### 4. 回溯重置到切片初始状态

这个定义足够清晰，适合服务端和客户端统一：
- 重置对象明确，包括足球和球员位置。
- 不污染前序切片结果。
- 也便于做幂等和断线恢复，因为切片状态不需要保存中间连续帧。

## 主要风险和建议

### P1 积分赛按“累计切片胜利数”计分，但不同关卡切片数会直接改变单票产出效率

当前规则：
- 积分赛积分 = 所有小关卡 `slice_wins` 累计。
- 基础关卡 `slice_list` 长度逐关可不同。
- 哨子默认生效，会额外增加 1 次非守门切片。

这会带来两个问题：
- 同样 1 张门票，不同关卡如果切片数不同，单票积分产出会不公平。
- 如果哨子是默认生效，所有关卡的真实积分上限都不是 `slice_list` 长度，而是“非守门切片数 + 1”，这会影响胜平阈值设计和排名增长速度。

建议二选一：
- 方案 A：积分赛所有正式关卡统一总切片数，例如全部 3 或全部 4。这是最省实现的方案。
- 方案 B：保留不同切片数，但排名积分改为标准化积分，例如 `rank_score = slice_wins / effective_slice_count * 100`。这会增加服务端和前端文案复杂度。

本次测试配置采用方案 A 的思路：绝大多数测试关卡固定 3 个有效积分切片，只用少量 4 切片关卡覆盖边界。

### P1 `slice_wins`、`goals`、`outcome` 三者关系还不够硬

文档里已经有：
- `level_result.goals`
- `level_result.assists`
- `level_result.slice_wins`
- `outcome = win/draw/lose`

但没有把这三者关系说死：
- 某切片若 `objective=pass_to` 成功，是否记 `slice_wins +1` 但 `goals +0`？
- 某切片若 `objective=keep_possession` 成功，是否仍可推高关卡胜利阈值？
- 关卡胜平负到底按 `slice_wins` 判，还是按 `goals` 判？

从积分赛与排名口径看，更合理的统一规则是：
- 关卡胜平负按 `slice_wins` 判定。
- `goals` 仅用于奖励和合同目标。
- 非 `score` 目标切片成功时，`slice_wins +1`，但 `goals` 不增加。

否则策划会很难同时配置“战术推进切片”和“进球类合同目标”。

本次测试配置按上述假设生成。

### P1 哨子默认生效的落点需要再明确

文档说：
- 哨子：增加 1 次非守门切片，默认生效。

但没有明确：
- 这 1 次切片是在关卡进入前就静态注入 `slice_list`，还是运行时临时加一片？
- 加入的是哪种切片，按预设池随机、按关卡配置固定，还是按当前关卡首个切片复制？
- 新增切片是否计入 `win_threshold / draw_threshold` 的设计基线？

如果不明确，客户端和服务端都会各自补逻辑。

建议：
- MVP 阶段把哨子做成关卡配置展开的一部分，不做运行时随机插片。
- 每关显式配置 `effective_slice_count` 或在出表工具中把“哨子展开后序列”直接写平。

本次测试配置直接把测试关卡写成最终切片序列，不依赖运行时插片。

### P2 “失败 = 被对方球员出球并踢出界外” 文案疑似有误

这句更像是“被对方球员断球并踢出界外”。

如果保持现在的写法，程序实现会不清楚：
- 失败原因枚举是否是 `goalkeeper_save / intercepted_out / timeout / wrong_direction` 这类离散值。
- 还是只分成功/失败，展示层自行猜原因。

建议补一个统一失败原因枚举，至少覆盖：
- `save_by_keeper`
- `intercepted_out`
- `out_of_bounds`
- `timeout`
- `wrong_direction`
- `hit_post`

这样音效、震动、回放文案和埋点才能统一。

### P2 `objective` 和 `modifier` 虽然正交，但缺少“组合白名单”

设计上正交是对的，但并不是所有组合都适合量产：
- `goalkeep + multi_target` 没意义。
- `throw_in + shrink_goal` 语义很弱。
- `penalty + keep_possession` 也不自然。

建议补一个最低限度的组合约束：
- 每个 `slice_type` 允许的 `objective_type`
- 每个 `slice_type` 允许的 `modifier_id`

本次测试配置已经尽量只使用语义稳定的组合。

### P2 排名界面还残留传统足球表头

钉钉文档已经明确提示了 `W/L/D/PTS` 不适用，但这不是纯 UI 问题：
- 如果外部运营、数值、前端、后端各自理解不同，最终会导致实际接口字段也混乱。

建议统一成以下任一口径：
- `Rank / Played / Slice Wins / Goals / Score`
- 或 `Rank / Matches / Slices Won / Points`

不要再保留传统 `W/D/L/PTS`。

## 测试配置策略

基于以上分析，测试关卡配置采用以下原则：
- 以钉钉文档为唯一规则源。
- 显式使用三层切片结构中的 `slice_preset` 与 `slice_instance`。
- 用 6 个关卡覆盖 6 类切片。
- 同时覆盖 5 类目标：`score / pass_to / hit_zone / keep_possession / survive`。
- 同时覆盖 4 类稳定 modifier：`wind / moving_keeper / no_aim_line / multi_target`。
- 大部分关卡固定 3 个切片，少量 4 个切片做边界验证。
- 统一假设关卡胜平负按 `slice_wins` 判，不按 `goals` 判。
